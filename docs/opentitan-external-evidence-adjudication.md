# OpenTitan External Evidence Adjudication

This project treats OpenTitan RTL execution as an external responsibility. The
sidecar only validates evidence that was already generated by a user-managed
runner or CI job. It does not compile a DUT, run RTL simulation, search or replay
failure-triggering sequences, or emit runner commands.

## CLI

```bash
verilator-model-sidecar adjudicate-opentitan-evidence \
  --target-contract /path/to/opentitan-targets.json \
  --evidence /path/to/evidence-bundle.json \
  --evidence-root /path/to/evidence-root \
  --output /path/to/adjudication.json \
  --report /path/to/adjudication.md
```

Multiple externally generated bundles can be summarized without running a DUT:

```bash
verilator-model-sidecar adjudicate-opentitan-evidence-set \
  --target-contract /path/to/opentitan-targets.json \
  --evidence /path/to/target-a-evidence.json \
  --evidence /path/to/target-b-evidence.json \
  --output /path/to/adjudication-summary.json \
  --report /path/to/adjudication-summary.md
```

The target contract can also be validated before any external evidence exists:

```bash
verilator-model-sidecar validate-opentitan-target-contract \
  --target-contract /path/to/opentitan-targets.json \
  --output /path/to/target-contract-report.json \
  --report /path/to/target-contract-report.md
```

A checked run specification can pin the target contract and evidence bundle list:

```bash
verilator-model-sidecar adjudicate-opentitan-run-spec \
  --run-spec /path/to/opentitan-adjudication-run.json \
  --output /path/to/adjudication-summary.json \
  --report /path/to/adjudication-summary.md
```

Stored machine-readable outputs can be self-validated without re-reading the
external evidence bundle:

```bash
verilator-model-sidecar validate-opentitan-adjudication \
  --adjudication /path/to/adjudication.json \
  --output /path/to/adjudication-validation.json \
  --report /path/to/adjudication-validation.md

verilator-model-sidecar validate-opentitan-adjudication-summary \
  --summary /path/to/adjudication-summary.json \
  --output /path/to/summary-validation.json \
  --report /path/to/summary-validation.md
```

Run specs are static JSON files:

```json
{
  "schema_version": 1,
  "surface": "opentitan_regression_adjudication_run_spec",
  "target_contract": "opentitan-targets.json",
  "evidence_root": "external-evidence",
  "evidence": [
    "tlul10818/evidence.json",
    "edn23526/evidence.json"
  ]
}
```

All run-spec paths must be relative, must not contain parent traversal or ASCII
control characters, and must resolve under their declared root. The command reads
only the declared JSON files and artifact paths referenced by the evidence bundles.

The repository also publishes structural JSON Schemas for the four external
input interfaces and the machine-readable output and validation surfaces:

- `contracts/opentitan_regression_target_contract.schema.json`
- `contracts/opentitan_regression_semantic_manifest.schema.json`
- `contracts/opentitan_external_regression_evidence_bundle.schema.json`
- `contracts/opentitan_regression_adjudication_run_spec.schema.json`
- `contracts/opentitan_regression_adjudication_run_spec_report.schema.json`
- `contracts/opentitan_regression_target_contract_report.schema.json`
- `contracts/opentitan_regression_adjudication.schema.json`
- `contracts/opentitan_regression_adjudication_summary.schema.json`
- `contracts/opentitan_regression_adjudication_validation_report.schema.json`
- `contracts/opentitan_regression_adjudication_summary_validation_report.schema.json`

These schemas define the file surfaces and required structure. Cross-file
semantic checks, canonical hashes, bad/fixed revision behavior, CPU/GPU
projection equality, seed linkage, and artifact byte verification are enforced
by the sidecar validator. The executable validator also rejects schema-unknown
fields on the contract, run spec, evidence bundle, and their declared nested
records; JSON Schema files are not merely documentation.

The command exits 0 only when the adjudication status is `pass`. It writes a
`fail` adjudication and report for malformed JSON or Contract violations, so a
stale passing output is not left behind. The adjudication JSON and Markdown
report include SHA-256 digests of the target-contract and evidence-bundle files
that were judged.

The adjudication JSON also includes a `checks` list. Each check has a stable
name, `pass` or `fail` status, and the issue codes that caused failure. The
current checks are `input_format`, `target_contract`, `bundle_identity`,
`semantic_cpu_gpu_equality`, `bad_fixed_oracle_delta`, `seed_corpora`,
`campaign`, and `hash_provenance`.

A passing adjudication also includes `verified_identity`. It records the exact
bad/fixed revision SHAs, checkpoint and oracle identities, campaign and
reproduction action domains plus their canonical hashes, declared semantic
observables, oracle field, and both semantic-manifest hashes. The human-readable
report prints the same revision and identity boundary. The stored-output
validator recomputes both action-domain hashes and cross-checks semantic-manifest
and graph/report source hashes against the verified artifact rows.
Passing stored adjudications require byte hashes for both the target contract
and evidence bundle. Passing summary rows require the same hashes and must match
the summary's target-contract hash. Run-spec summaries additionally bind the
run-spec hash. Unknown hash roles, empty provenance maps, and missing required
hashes fail validation.

The evidence-set summary exits 0 only when every bundle passes. Its JSON records
the target-contract SHA-256, per-bundle status, per-bundle input hashes,
per-bundle issue details, pass and fail counts, and aggregate check pass/fail
counts.

The Python API also exposes `validate_adjudication_document` and
`validate_adjudication_summary_document` so stored machine-readable outputs can
be checked for self-consistency after generation. These checks verify status,
issue counts, check issue-code linkage, summary pass/fail counts, input hashes,
and verified-artifact rows.

The run-spec summary additionally embeds the run-spec validation report and the
target-contract validation report. A target contract that contains an invalid
unused target still fails the run, because the contract file is the authority for
the whole adjudication set.

## Target Contract

The target contract root is a JSON object:

```json
{
  "schema_version": 1,
  "surface": "opentitan_regression_target_contract",
  "targets": [
    {
      "target_id": "tlul10818",
      "ip": "tlul",
      "issue": "10818",
      "revisions": {
        "bad": "lowercase40hex",
        "fixed": "lowercase40hex"
      },
      "checkpoint_identity": "checkpoint:v1:name",
      "oracle_identity": "oracle:v1:name",
      "campaign_action_domain": ["action_a", "action_b"],
      "reproduction_action_domain": ["action_a"],
      "semantic_observables": ["observable_a", "observable_b"],
      "oracle_field": "oracle_violation",
      "semantic_manifest_sha256": {
        "bad": "lowercase64hex",
        "fixed": "lowercase64hex"
      }
    }
  ]
}
```

`validate-opentitan-target-contract` checks every target in the file, including
duplicate `target_id` values and targets that are not yet referenced by an
evidence bundle.

The validator requires exactly one matching target. The evidence bundle must
match its issue/IP, revision SHAs, checkpoint identity, oracle identity, action
domain order, action-domain hash, and both semantic manifest hashes.
The bad and fixed revision SHAs must be distinct.

## Semantic Manifest

The `semantic_manifest_bad` and `semantic_manifest_fixed` source artifacts are
strict JSON objects with surface `opentitan_regression_semantic_manifest` and
integer schema version 1. Each manifest binds:

- the target ID, revision label, and exact revision SHA;
- the checkpoint and oracle identities; and
- an ordered observable list containing `name`, `semantic_id`, and a
  positive integer `width_bits`.

Observable names must equal the target contract's `semantic_observables` in
order, followed by its `oracle_field`. Names and semantic IDs must be unique.
The manifest bytes must also match the corresponding target-contract SHA-256.
Consequently, a matching opaque hash alone is insufficient: malformed JSON,
revision drift, and observable-binding drift all fail adjudication.

## Evidence Bundle

The evidence bundle root is a JSON object with surface
`opentitan_external_regression_evidence_bundle` and integer schema version 1. It must
provide:

- `runner.status: "pass"` plus nonempty `runner.identity` and
  `runner.completed_at` fields from the external runner.
- `revision_results.bad` and `revision_results.fixed`, each with executed
  sequences, oracle-failure sequences, and CPU/GPU observations.
- CPU/GPU projections whose JSON types and values match exactly for every
  target-declared `semantic_observables` key. In particular, JSON `true` is not
  equal to integer `1`. Every executed action sequence must have exactly one
  corresponding semantic observation.
- A target-declared `oracle_field` whose CPU and GPU values match and are 0 or
  1.
- A bad revision with at least one oracle failure and a fixed revision with no
  oracle failures. Every declared failure sequence must have a corresponding
  semantic CPU/GPU observation. Conversely, every asserted bad-revision oracle
  observation must be listed as an oracle failure.
- Separate `seed_corpora.coverage_gain` and
  `seed_corpora.oracle_violation` lists. The same sequence may appear in both
  lists; separation is by corpus kind, not by disjoint action sets. Each seed
  entry carries integer `schema_version: 1`, and both lists must be nonempty.
  `oracle_violation` sequences must use only actions from the target contract's
  `reproduction_action_domain`. Each oracle-violation seed must be a bad-revision
  failure and must also be executed and observed on the fixed revision without an
  oracle failure. `minimal: true` is verified rather than trusted: the seed must
  be 1-minimal under single-action deletion. Every nonempty sequence obtained by
  deleting one action must have been executed and observed on the bad revision,
  and none may assert the oracle or appear in its failure list. A one-action seed
  is trivially 1-minimal within this nonempty sequence domain.
- Nonempty `source_artifacts`, `graph_artifacts`, and `report_artifacts` lists.
  Artifact paths are relative to `--evidence-root`, must contain no parent
  traversal, must stay under that root, and must match their declared SHA-256.
  `source_artifacts` must include
  `semantic_manifest_bad`, `semantic_manifest_fixed`, `equivalence_report`, and
  `campaign_report` roles. Semantic manifest artifact bytes must match the
  target contract's bad/fixed `semantic_manifest_sha256` values. Graph and
  report artifacts also carry a `payload` object and a `payload_sha256` field
  equal to that payload's canonical JSON SHA-256. The payload must declare
  `source_artifact_role` or `source_artifact_roles`, and every referenced role
  must exist in `source_artifacts`. It must also declare the exact source
  artifact SHA-256 with `source_artifact_sha256` or
  `source_artifact_sha256_by_role`, and those hashes must match
  `source_artifacts`.
- Passing stored graph/report rows retain a nonempty map from every declared
  source role to its verified source-artifact SHA-256. Source rows cannot carry
  derived-artifact provenance fields.
- Campaign policies must include raw action `orders`. Each order must equal the
  target contract's `campaign_action_domain` as a full permutation; `mean`,
  `p50`, `p95`, and `max` must be finite values within one action and one full
  domain pass; `p50 <= p95 <= max`; `mean <= max`; and `long_tail_rate` must be
  a finite value in `[0, 1]`.

The JSON parser rejects duplicate keys, invalid UTF-8, lone Unicode surrogates,
and non-finite numbers, including overflowed exponent notation. Declared paths
also reject ASCII control characters.
